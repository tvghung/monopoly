# HTTP, LAN and online hosting

The desktop app starts one Electron utility-process helper. The helper binds the game HTTP/Socket.IO server to `0.0.0.0` on an OS-selected port, serves the bundled client, and answers room-code LAN discovery. The host renderer connects over `127.0.0.1`; other LAN devices use a real private IPv4 endpoint. The helper creates a fresh RAM store on start. Its exit ends every match; desktop reports a terminal host failure and never performs same-match helper recovery.

## HTTP surface

- `/healthz` returns `ok` while live and 503 during shutdown.
- `/readyz` returns `ready` while the live store/server is ready and 503 during shutdown.
- `/_otb/room?code=<ROOM_CODE>` is a rate-limited desktop probe for a known room code. It returns 404, or 200 with `{instanceId}`: a random id of this helper process (`runtime.instanceId`), never game state or a credential, and **never proof of anything** (no CORS; Electron main reads it).
- `/_otb/continuity?code&challenge&endpoint` (desktop profile, same limiter) answers a relinking client: 400 for a bad code, a challenge that is not 43 base64url characters or a long endpoint; 403 (empty) when `endpoint` is not one of this process's own addresses (`services/hostContinuity.ts`: own IPv4 or 127.0.0.1 with the listening port, or the tunnel origin set by the helper message `public-endpoints`); 404 for an unknown room; 503 while shutting down; else 200 `HostContinuityProof` (`packages/shared/src/hostContinuity.ts`) signed with the per-process P-256 key whose public half the resume ACK gives as `hostContinuityKey`. CORS reflects only the game's own origins. Tests: `hostContinuity.integration.test.ts`. The host checks it through the public route before publishing an online link, and the desktop Join compares the ids of a LAN and an Online answer for the same code: equal ids are one Host (joined over the LAN), different ids stay an explicit ambiguity.
- Static assets and the SPA fallback share the game server origin. Socket.IO uses its default path and is not throttled by the static asset limiter.

## LAN

The desktop chooses and advertises usable IPv4 interfaces, not loopback. Automatic port selection retries bounded bind conflicts. A desktop Join can discover a room by code through UDP; a full LAN invitation connects directly. LAN play and discovery require no Internet or Cloudflare account.

## Online

The package bundles a pinned, SHA-256 verified official `cloudflared` binary for Windows x64, macOS x64 or macOS arm64. [`apps/desktop/cloudflared-integrity.json`](../../../apps/desktop/cloudflared-integrity.json) is the only trusted reference: per target it pins the official download (`archiveSha256`), the executable inside it (`executableSha256`; the two are equal on Windows, where the asset is the executable, and differ for the macOS `.tgz`), and the license text (`licenseSha256`). `prepare:cloudflared` verifies the download before anything is written, verifies the extracted executable, and removes a cached copy that does not match, so no unverified executable is left in `generated/`. A `cloudflared.sha256` file beside the executable is only a build-log record: the app, the package check and the preparation script never trust it, so rewriting both files together is rejected. The desktop resolves the executable only from its own resources (never from `PATH`) and re-hashes it against the manifest immediately before every launch.

The desktop launches a Quick Tunnel without a shell or manual installation. Each run gets its own private temporary directory holding an empty `config.yml`, passed as `cloudflared tunnel --no-autoupdate --config <that file> --url http://127.0.0.1:<port>`, and the child environment drops every `TUNNEL_*` variable plus `NO_AUTOUPDATE` and `NO_TLS_VERIFY` (the variables `cloudflared tunnel --help` lists). Measured with cloudflared 2026.9.3 on 2026-10-08: a user-level `~/.cloudflared/config.yml` containing `name:` or an exported `TUNNEL_NAME` made `tunnel --url` exit 1 ("Cannot determine default origin certificate path") before printing a URL; the empty `--config` file removes the first cause and dropping `TUNNEL_*` removes the second, and the user's own configuration files and environment are never read, changed or deleted. The directory is deleted when that tunnel exits or stops, and a late exit of a stopped tunnel can neither remove the directory of nor report a loss for its replacement. The Host retries public DNS/page/readiness checks for a bounded period, then checks the actual room through the public endpoint. Only then may the lobby copy a direct `https://<host>.trycloudflare.com/?room=<code>` link. The browser loads the client and Socket.IO from that same HTTPS origin.

Complete links bypass the optional registry ([services/room-registry](../../../services/room-registry/README.md), deployed by the owner; a build carries its URL from `OWN_THE_BLOCK_REGISTRY_URL` in `release-config.json`, the runtime variable wins). If configured, the registry resolves a bare online room code across networks and serves `/join?room=<code>`. A code another live room already holds fails the start with `CODE_TAKEN` (the launcher draws a new code); any other registry failure never blocks or hides direct-link hosting: the link and QR stay, `onlineState` is `DISCOVERY_UNAVAILABLE` until a renewal succeeds, and `discoveryConfigured` tells the lobby whether code lookup exists at all. Which public origins are acceptable is `packages/shared/src/endpointPolicy.ts` (Quick Tunnel = `experimental`); the desktop adapter mirrors it under a contract test. A tunnel loss hides the old link, keeps the RAM match, and attempts bounded reconnection. If Cloudflare issues a new hostname, the host receives a new link. A guest whose reconnection keeps failing for 20 s is offered to paste the new invitation of the same room in the reconnect overlay (the desktop app also asks the registry): the client stores its token for the new origin in its own storage and reconnects there, so it resumes its seat; the token never travels in a URL. Quick Tunnels are documented by Cloudflare as development/testing infrastructure, without an uptime guarantee. Stable production hosting would need a named tunnel and its account/domain setup.

The server permits the packaged `app://own-the-block` renderer and exact LAN/tunnel browser origins. Incoming commands remain schema checked and actor authenticated. A new desktop room requires Electron main's process-scoped capability for the host-selected code; peer address, `Origin` and forwarding headers never grant it, so Cloudflare's loopback forwarding cannot supply it (see [socket session](./socket-session.instruction.md)).

### Client identity and request limits behind the tunnel

Engine.IO reports `handshake.address` as the raw TCP peer, so every visitor arriving through the local connector looks like `127.0.0.1`. The server therefore derives one limiter key per connection in `socket/clientIdentity.ts`:

- A non-loopback peer (a LAN device talking to the game port) is keyed by its own address. Whatever headers it sends are ignored, so it cannot invent another identity.
- A loopback peer may name the visitor behind it only when the process was started by an Online Host (`OTB_ONLINE_ROOM_CODE` is set; the desktop profile only), and only through `CF-Connecting-IP` holding exactly one valid IP address. Measured through a real Quick Tunnel: Cloudflare's edge sets that header to the address it saw and answers `403` (`error code: 1000`, for HTTP and WebSocket upgrades) to any request that arrives already carrying one, so the origin never receives a visitor-chosen value. `X-Forwarded-For` is not used (Cloudflare appends the real address after whatever the visitor sent) and neither is `True-Client-IP` (a visitor-sent value passes through unchanged).
- Other loopback traffic (the Host's own window, a local probe) shares one `local` key. Without an Online Host, no header is read at all.
- IPv4-mapped IPv6 collapses to IPv4 and other IPv6 addresses are grouped by /56, so a household cannot mint unlimited keys from its prefix.

Room admission (`join room`) is limited by this key (30 attempts per minute, shared by players behind one public address), by the connection (8 per minute) and by the process (600 per minute as a backstop, so a flood needs 20 or more distinct visitors to starve everyone). The limiter holds at most 1,024 client keys (further keys share one overflow bucket), expires entries lazily, and records only admitted attempts. The `/_otb/room` probe (60 per minute) and the static-asset limiter use the same key, so one visitor cannot exhaust the Host's readiness probe or the page for the others.

The optional live probe is `scripts/proveQuickTunnel.mjs`; it verifies a public page and four Socket.IO clients through a real Quick Tunnel. Cross-network desktop/mobile acceptance still requires physical devices on independent networks. The retired Docker/Render deployment and PostgreSQL setup are outside the current architecture.
