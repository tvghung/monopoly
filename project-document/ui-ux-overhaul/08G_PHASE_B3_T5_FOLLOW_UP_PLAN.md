# 08G — Phase B3 follow-up: time-to-playable (T5) plan

> **REFERENCE** — A plan with an execution record: the sections before [Results](#results-2026-10-18) are the plan as it was approved; the
> Results section records what was done, measured and decided. The plan is written to be executed by a developer or an agent that reads only this file and
> the documents it links ([08F](./08F_PHASE_B3_IMPLEMENTATION.md) is HISTORICAL). Targets T1–T5 are defined in [08E §11.1](./08E_PHASE_B3_INVESTIGATION.md); the measuring tools are in
> [scripts/perf/README.md](../../scripts/perf/README.md).

## Description

B3 removed the cold-launch freeze (longest active frame 2613 → 108 ms median, 0 program links after `otb:warmup:done`) but made
**time-to-playable (T5) worse**: median 2162 → 3747 ms, P95 2228 → 3867 ms on the measuring machine, against a limit of +10 % of the baseline P95
(2451 ms). This plan covers how to close that gap: the options listed in 08F §7.4, ordered, with the evidence each one needs, what it can and
cannot buy, the decisions that belong to the owner, and approval gates. It starts with the option the owner asked to see first, compiling against a
placeholder environment so that the compile overlaps the studio PMREM, and shows with arithmetic from the 08F medians that **that option alone cannot reach T5**.

## Context

- The page, in B3 medians ([08F §5](./08F_PHASE_B3_IMPLEMENTATION.md#5-cold-launch-before-and-after)): React mounted at 0.86 s; the canvas exists and the first PMREM
  program links at **2.19 s**; the studio PMREM then blocks the main thread for **0.91 s**; the warm-up runs **0.66 s** (the compile and first-use finishing of the scene and fixtures take most of it, texture upload 0.1–0.19 s; the exact split of the rest is not recorded); `otb:warmup:done` and the first drawn frame at **3.75 s**. `main` drew its first frame at 2.17 s and
  froze for 2.6 s twice afterwards.
- T5 is measured by `b3Baseline.mjs` as navigation start to the first board frame at or after `otb:warmup:done` (08E §11.3). Same-machine baseline P95
  2228 ms; limit 2451 ms. The original machine (Core i5-10210U, 2044 ms limit) has still not been available; every figure is main against the branch on one machine.
- The PMREM is generated by `StudioEnvironment` (`apps/client/src/game/scene/render/environment/StudioEnvironment.tsx`) from a procedural scene
  (`createStudioEnvironmentScene.ts`, built from `OTB_PALETTE` and `LIGHT_RIG`), chosen so that the game needs no asset, no loader and no CSP change. A lit
  material's program depends on the environment: `WebGLPrograms.getParameters` folds `envMap` presence, `envMap.mapping` and, for CubeUV maps, `envMap.image.height` into the
  program key (verified in `three@0.185.1`, `src/renderers/webgl/WebGLPrograms.js` lines 62–64, 217–219, 442–443). That is why no lit program can be compiled before an environment of the right
  layout exists, and why 12 pre-environment variants are never needed once the environment exists (08F §7.3).
- The PMREM layout is fixed by `PMREMGenerator._allocateTargets`: with the default `size = 256`, `cubeSize = 256`, a render target of `3 × max(256, 112) = 768` by `4 × 256 = 1024`
  (`CUBEUV_TEXEL_HEIGHT 0.0009765625` in the recorded defines), `texture.mapping = CubeUVReflectionMapping`.
- The coin materials hold their own `envMap` (`applyCoinEnvironmentMap` in `apps/client/src/game/scene/stations/coinVisuals.ts`, called by `applyStudioEnvironment`), so any
  approach that swaps the environment must swap theirs too.

## Purpose

Decide, with measurements instead of estimates, which combination of changes brings cold time-to-playable inside the owner-approved limit, without giving back T1/T2 or
changing what the board looks like, and stop pursuing options the measurements rule out.

## Desired Outcome

- T5: cold time-to-playable P95 ≤ 1.10 × the same-machine `main` P95 over at least 20 alternating launches (and, when that machine becomes available, ≤ 2044 ms on the original one), or a
  documented PARTIAL with the remaining gap quantified and the owner's decision recorded.
- T1 (≤ 300 ms), T2 (0 links after `done`), T4 (no resource growth, visuals identical or explained) still pass; `pnpm perf:warmup-check` still passes 32 of 32 or more.
- Every claimed gain is a measured difference between two bundles measured alternately.

## Execution guide

Work on a new branch from the B3 branch (or from `main` once PR 19 is merged). One task per commit. Measure with the alternating protocol of
[08F §11](./08F_PHASE_B3_IMPLEMENTATION.md#11-reproduce): a `main` or B3 reference bundle against the candidate, 20 launches each, empty Chrome profile per launch, same machine. Do not
compare numbers from different machines or sessions.

### Task 0 — decompose the 0.86 s to 2.19 s (no behavior change; 1 hour)

Add production-safe `performance.mark` calls (dev/UAT-only if they cost anything) at: the scene chunk request and evaluation (`import('../game/scene/GameScene')` in
`apps/client/src/components/BoardRenderSurface.tsx`), `GameScene` first render, `Canvas` `onCreated`, the first commit of `Board3D`, the start and end of the `StudioEnvironment` effect.
Report the medians over 20 cold launches in a short table in this file's results section.

- Acceptance: the chunk fetch, parse, React/scene construction and renderer creation times are each reported; Option C's ceiling is stated as a number.
- Decision it feeds: whether C is worth doing at all (if the 1.33 s is mostly scene construction that cannot move, C gains little).

### Task 1 — spike A: placeholder environment (time-boxed to half a day; throwaway branch)

1. Create a placeholder texture of the PMREM layout: `mapping = CubeUVReflectionMapping`, `image = { width: 768, height: 1024 }`, the PMREM target's type, format and color space, before the PMREM effect runs
   (the warm-up must start first: a component placed before `StudioEnvironment`, or a first pass inside its effect before `fromScene`).
2. Assign it as `scene.environment` and as the coin materials' `envMap`, call `renderer.compile` for the scene and the fixtures, restore, then let the real PMREM run and replace both.
3. After the real environment is applied, assert in a unit test and in the probe that compiling the scene again adds **0** programs, i.e. the keys matched.
4. Measure time-to-playable and the warm-up window against the B3 bundle, alternately, 20 launches each.

- Acceptance to **keep** it: P95 time-to-playable at least 0.2 s better, `warmupCheck` still 32 of 32, tier switches and context restore unchanged, no more than a handful of lines in `StudioEnvironment` and the runner, and a unit test that fails if the placeholder's layout stops matching `PMREMGenerator` (compare against a real generated target in a WebGL-less way by reading the generator's constants, or fail the probe).
- Otherwise **drop it**, record the measured gain in the results section, and do not carry the code into the main line.

### Task 2 — option B: baked environment (after owner approval, §Decisions 1)

1. A build-time generator script produces the CubeUV texture from `createStudioEnvironmentScene()` using the same `PMREMGenerator` on a headless WebGL context (or a one-off Playwright page) and writes
   an asset (candidate encodings in §Decisions 2). The generator is deterministic and its output is committed or produced by `pnpm build`.
2. `StudioEnvironment` loads the asset (or decodes it from a module) into a `DataTexture`/`CompressedTexture` with `mapping = CubeUVReflectionMapping` and the exact target properties, applies it the same way
   (`applyStudioEnvironment`), and falls back to the procedural PMREM if loading fails (the layer must keep failing soft inside `OptionalSceneLayer`).
3. A test asserts that the baked texture's metadata equals what the generator produces, and a consistency check (script or test, run in CI) regenerates it from `OTB_PALETTE` and `LIGHT_RIG` and fails when the committed asset is stale.
4. Remove nothing from the procedural path: it is the fallback and the generator.

- Acceptance: pixel comparison `captureCompare.mjs` against the B3 bundle with the settled states bit-identical or within a tolerance the owner approves (the baked data should be bit-identical if stored as half-float
  without re-encoding); `warmupCheck` 32 of 32; no CSP or packaging change, or the change is reviewed (desktop `app://` handling in `apps/desktop`); the PMREM programs are absent from the cold signature set; the longest long task at load drops from about 1.25 s; time-to-playable measured alternately.
- The expected result is about 2.9–3.0 s: record the measured one honestly, whatever it is.

### Task 3 — option C: earlier scene creation (after Task 0, only if its ceiling justifies it)

1. Decide the trigger with the owner: the lobby screen, the room-ready event, or idle time after the app shell loads. The harness path cannot show a gain; add a lobby-to-board measurement route (a UAT page that
   mounts the lobby first, then the board) and define T5-lobby in this file before measuring.
2. Prefetch the scene chunk only (a plain `import()` of `GameScene` at the trigger); measure; create the renderer early only if the chunk alone is not enough (this is where the
   "no throwaway WebGL contexts" principle of the 08A target architecture applies: the early renderer must be the one the board keeps).
- Acceptance: lobby-to-board time-to-playable measured alternately; memory and context count unchanged when the player never starts a match (prefetch must be skipped on constrained devices).

### Task 4 — decision gate: B + C measured

If the combination is within 1.10 × the baseline P95, finish with a record (08H) and update the checklist. If not, write the remaining gap and bring option D (or a revised T5 definition) to the owner; do not implement D without an
explicit amendment of 08E §11.1.

### Task 5 — documentation and regression guard (with every task that lands)

Update `project-document/monopoly-websockets/Client/game-board.instruction.md` ("Shader warm-up") and the B3 section of the client testcase checklist; add the new marks (if any) to the list in 08F §3.5; keep
`pnpm validate:docs` green.

## Measurement protocol

- Bundles: UAT, unminified, built with `VITE_PHASE4_UAT=1`; reference and candidate alternately, 20 launches each, a new Chrome process and empty profile per launch.
- Report min / median / P95 / max of time-to-playable, the warm-up window, the longest active frame, the longest long task, links before and after `done`, programs after the second turn.
- A gain smaller than the spread between the 20 runs of one bundle (about 0.2 s at P95 on the measuring machine) is not a gain.
- Always run `pnpm perf:warmup-check` on a candidate before measuring it: a bundle that links after `done` is not comparable.

## Decisions for the owner (recommended defaults)

1. **May the game ship a baked environment asset instead of the procedural one?** Recommended: **yes**, as an asset produced and verified by the build, with the procedural path kept as a fallback and generator. Without it, T5 cannot pass.
2. **Encoding of the baked texture** (if 1 is yes): recommended **half-float RGBA, uncompressed** first (768 × 1024 × 8 bytes ≈ 6 MB raw, bit-identical to what the generator produces); try a lossless or near-lossless
   compressed form only if the size matters and the pixel comparison stays inside the approved tolerance.
3. **Which "T5" counts for a real match** (a lobby precedes the board): recommended to keep the harness T5 as the gate and add a lobby-to-board figure as the product metric.
4. **If B + C still fall short**, accept PARTIAL with the first stable frame as the reported alternative (3.9 s against 7.4 s on `main`), or amend T5. Recommended: report both and keep T5 FAIL/PARTIAL until the owner amends it.
5. **Original baseline machine:** run the final protocol on it once; until then no absolute 2044 ms claim is made.

## Approval gates

1. After Task 0: owner reads the decomposition and confirms whether C is pursued.
2. Before Task 2: owner answers Decisions 1 and 2 (asset, encoding, packaging review).
3. Before merging anything from Task 1: only if its acceptance is met; otherwise the branch is deleted and the measurement kept.
4. After Task 4: owner accepts PASS, PARTIAL or an amended target.

## Risks

- B's asset can go stale when `OTB_PALETTE` or `LIGHT_RIG` change: the consistency check in Task 2 must run in CI.
- Option A, if kept, couples the warm-up to three's key fields; any three.js upgrade must re-run the "0 programs added" test.
- Earlier work on the main thread may hurt other first-load paths (the lobby, the audio engine): Task 3 must measure the lobby, not only the board.
- Results on one machine do not transfer: repeat on the original machine before any absolute claim.
- Nothing here changes gameplay, the protocol, persistence or the FPS scheduler.

### Task 1 — spike of the placeholder-environment overlap: dropped

Compiling the scene against a CubeUV placeholder before the PMREM (URL flag, same bundle on and off, 20 launches each; [off](./08G_evidence/task1-spike-off.json),
[on](./08G_evidence/task1-spike-on.json)): the warm-up window shrank from 684 to 525 ms, but `gl.compile` itself blocked the main thread for 163 ms and the queued
compiles slowed the PMREM from 910 to 1265 ms: **done moved from 3800 to 3939 ms (+139 ms)**. It missed its acceptance bar (at least 0.2 s better) by a wide margin and was deleted. The prediction of
the plan, that this option cannot reach T5, held; the measurement adds that it does not help at all on this machine, because the GPU process is the shared resource.

### Task 2 — baked environment: done

- `bakedStudioEnvironment.ts`, the asset (`studio-environment.cubeuv.f16.z`, 471 KB deflated from 6.3 MB of half-float RGBA) and its metadata; `StudioEnvironment.tsx` uploads it as a `DataTexture` with the PMREM
  texture's properties and falls back to filtering the studio when the file is stale (hash of the studio's inputs), missing or cannot be decompressed; `scripts/bakeStudioEnvironment.mjs` regenerates it (two bakes in one
  browser are byte-identical). A hash test fails when an input of the picture changes without a re-bake. The warm-up waits for the environment (`WarmupHost.waitForEnvironment`).
- **No CSP or packaging change is needed (read, not packaged):** the file is fetched same-origin, which the desktop CSP allows through `connect-src 'self'`, and the desktop's `app://` handler serves an unknown extension as `application/octet-stream` (`apps/desktop/src/rendererContentType.ts`). `pnpm desktop:package` and a packaged run were not done.
- **Baked and procedural environments render pixel-identically** at Low, Balanced and High (0 of 921 600 pixels differ, with a forced frame), and the settled-state comparison against `main` shows the same differences as in 08F §8 and no new one.
- Effect: PMREM step 924 → 70 ms; time to the first frame 3877 → **2883 ms** (median of 20; [raw](./08G_evidence/task2-decomposition-baked-env.json)).

### What is left of the 371 ms, measured

After the changes the first frame is at 2613 ms: about 1.2 s before the warm-up starts (page boot 0.5 s, the board's WebGL context and renderer 0.4–0.6 s, the React build of the scene 0.2 s) and about 0.7 s of warm-up
(GPU compile wait about 0.25 s, finishing the programs 0.18 s, texture upload 0.07–0.19 s, the rest in between). Candidates, each a separate decision, none done:

1. **The board's own WebGL context (about 0.43 s of blocked main thread):** the renderer is created with `powerPreference: 'high-performance'` and `antialias`; whether a different request is cheaper on hybrid-GPU laptops is a graphics-policy change and needs a measurement on the target machines before anyone decides.
2. **The remaining generators (about 0.14 s):** the district pattern (40 ms), the rest of the table texture (about 70 ms) and the pebble tests: further exact optimisation, or generation in a worker while the context is created (the main thread is blocked in `getContext` for 0.4 s, a worker would not be).
3. **Creating the canvas and scene before the board is shown (option C reframed):** can move the whole 1.2 s into a lobby in a real match; needs a lobby-to-board measurement path and an owner decision about holding a renderer early.
4. **The warm-up (0.7 s):** its floor is the GPU compile and the first-use finishing of 26 programs; fewer programs (for example sharing variants) is the only lever, and each removed variant has to be shown to be unused.
5. **Redefine "playable" (option D):** the first stable frame and T5 now nearly coincide: 12 of 20 launches have no frame of 100 ms or more at all, and in the other 8 the last one ends at 2749 ms (median), about 0.1 s after the first playable frame (the first frame itself costs 100–140 ms). The 3.6 s head start over `main` that option D relied on in 08F is no longer a separate argument.

Items 1 and 2 together are estimated (unmeasured) at 0.2–0.4 s, which is the size of the gap. They are the next measurements to take, in that order of effort.

The original baseline machine is still not available. A 0.4–0.6 s main-thread block remains at load (the board's context creation and the React build), and the latent text-invalidation defect of `main` (08F §8, §10) is untouched.
